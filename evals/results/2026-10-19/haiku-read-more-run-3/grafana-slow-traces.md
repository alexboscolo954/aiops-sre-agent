## p99 latency on GET /product/{sku} in storefront is driven by slow inventory-db queries. The trace spans show the inventory service's SELECT stock ... FOR UPDATE waiting on Lock:tuple for about 3 seconds, and roughly 3 in 10 storefront requests in the last hour are slow (2.5 to 3.3s). Lock contention in inventory-db is the likely cause, but I did not confirm the trigger or the lock holder.

**Root cause** (medium confidence, `dependency_failure`): Requests to GET /product/{sku} are blocked in inventory's stock query. In trace 45d31a48f074c35561c0353b3bdfe298 (3103ms total), the storefront span takes 3103ms and calls inventory GET /stock/{sku} for 3056ms. Inside that, the child span SELECT stock (db.query.text 'SELECT qty FROM stock WHERE sku = $1 FOR UPDATE', server.address inventory-db.shop.svc) runs 3050ms with db.wait_event 'Lock:tuple'. The catalog (14ms) and pricing (21ms) calls are fast, so the time is spent waiting on a row lock in inventory-db, not on the storefront app. The slow pattern is consistent across traces: Tempo returned about 10 traces over 2.4s in the last hour, and storefront logs show lines like 'GET /product/sku-1010 200 2606ms slow' alongside normal '~60ms ok' lines. I found no Kubernetes rollout data in these tools, so I cannot say whether a recent deploy changed the locking behaviour. The lock holder is also unidentified, so the cause is inferred from the wait event.
**Severity:** high  ·  **Affected:** shop/Deployment/storefront, shop/Deployment/inventory, shop/StatefulSet/inventory-db

**Recommendations**
1. Check inventory-db for lock waits and blockers now, for example pg_stat_activity filtered on wait_event_type='Lock' and pg_blocking_pids(), to identify the long-running transaction holding the row locks on the stock table.
2. Find what changed: check the inventory Deployment rollout history and any recent batch or migration jobs that update stock rows, since no rollout data was available to me.
3. Shorten the lock wait in the inventory code path, for example with a lock_timeout or SKIP LOCKED, or drop FOR UPDATE on this read if it is not needed. Any change here should go through normal review.
4. Add log or metric coverage for inventory and inventory-db, since no inventory log stream was visible to these tools.
5. Check the Prometheus p99 for storefront and inventory to confirm the timing and when it started. I did not run Prometheus queries.
