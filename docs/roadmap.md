# Roadmap

The goal is one Hub that lets the Operator run SRE for several Contracts at once. It answers alerts, answers questions and runs checks, and it never lets one Contract's data reach another. From Phase 9 it also optimizes each Contract's resources: Sizings for every Workload, cost, horizontal scaling, nodes, spot and GPUs, applied under the Operator's Automation. HolmesGPT, OpenSRE and IncidentFox inspire the agent; ScaleOps (first) and Kubex inspire the optimizer. We take their ideas, not their code.

Terms are defined in [`CONTEXT.md`](../CONTEXT.md). The decisions behind the shape are in [ADR 0002](adr/0002-hub-and-relay.md) (Hub and Relay), [ADR 0003](adr/0003-contract-data-in-private-git.md) (Contract data in a private repo) and [ADR 0004](adr/0004-standing-approval-for-sizing.md) (an in-cluster Actuator applies Sizings under a standing approval).

## Where we start

| Today | Needed |
|---|---|
| `Settings` is global: one kube context, one namespace list, one Runbooks dir, one Slack webhook, one pair of tokens | Everything except Hub settings is set per Contract |
| `triages` and `recent` live in memory. Dedup is keyed by `groupKey` alone | Postgres, keyed by Contract. Two Contracts can send the same `groupKey` |
| `InMemorySaver` checkpointer. A restart loses pending approvals | Postgres checkpointer. Pending approvals survive a restart |
| `read_only(tool)` trusted the server's `readOnlyHint` | Done in 0.2: the Hub's own list decides read or write, and a server can only make a tool stricter |
| `replay_server` builds tools from our in-process servers | Replay also builds them from saved schema snapshots of vendor servers |
| Alerts only, Slack webhook only, API for approvals | Triage, Question and Check, with Slack and a web console |

## How every slice ships

A slice is one commit-sized change, about one working session (1 to 3 hours).

1. **Glossary first.** New terms go in `CONTEXT.md` before code. Add an ADR only when the decision is hard to reverse, would surprise a reader, and came from a real trade-off.
2. **Tests for every branch of new logic.** Mutation-check each new test: remove the logic, and the test must fail.
3. **An isolation test** for anything that stores, reads or sends Contract data. It uses the two demo Contracts and proves Contract A's data never reaches Contract B, whether in prompts, tools, storage or notifications.
4. **Rerun the real eval suite** when anything the model sees changes: the prompt, tool names, descriptions or schemas, or the Report schema. Commit the results under `evals/results/`. No Scenario may regress.
5. **Keep lint and the full suite green.** Update the docs (`docs/*.md`) and the config table.
6. **Write a one-line commit subject.** CI must be green before moving on.

**Where checks run.**
- **CI**, in the public repo: lint, unit and isolation tests, the kind demo integration and the deploy smoke test. These run on the two synthetic demo Contracts only.
- **Locally:** the real-LLM evals (they need the API key), and Contract Scenarios from the private contracts repo.

## Decisions

| Topic | Decision |
|---|---|
| Who works | One Operator. The Operator receives every Report and makes every Approval decision |
| Reaching a Contract | **Direct** (the Hub holds the credentials) or **Relay** (dials out from the client network) |
| Hub | Any machine you own, a VM or a laptop: docker compose with the Hub and Postgres |
| Operator interfaces | Your own Slack workspace, one channel per Contract, with approve buttons. Also a web console |
| Client delivery | Optional per Contract. A Client report goes when the Operator clicks Send, never with approval controls |
| Data policy | Set per Contract. Default: no restrictions |
| Integrations | Hybrid: vendor MCP servers where they're good, our own where they're missing |
| Contract config | YAML per Contract in one private repo, with SOPS secrets and an age key per Contract |
| Console | View and act. It shows config read-only and is reachable only over Tailscale |
| Investigations | Triage, then Question, then Check |
| Knowledge | Similar incidents and Teachings stay in their own Contract. Teachings need review. Shared knowledge is written by the Operator |
| Optimizer shape (2026-10-21) | The brain in the Hub (metrics aggregates, recommender, Sizing policies), the hands in the client cluster (an Actuator that pulls approved Sizings over the Relay). [ADR 0004](adr/0004-standing-approval-for-sizing.md) |
| Writes under Automation | Allowed, opt-in per Contract and per Workload, read-only by default, audited and reversible. Reflexes (OOM step-up, burst CPU, startup boost, auto-rollback) act unattended, capped and expiring |
| Metrics for Sizings | Each Contract's own Prometheus; the Hub keeps per-Workload aggregates in Postgres, never raw series. A bundled collector only where a cluster has none |
| Sizing policies | In the contracts repo (`contract.yaml`), validated by `aiops contracts validate`; the Actuator renders them in the cluster |
| Applying Sizings | In-place resize first (Kubernetes 1.33+); webhook plus PDB-safe eviction only behind a per-Contract flag. Never Git write-back to client repos |
| Actuator | Python, same image as the Hub (`aiops actuator`); revisit only if webhook latency shows up in tests |
| Scope | Everything both products do: Workloads, horizontal, node and Karpenter, spot, cloud billing, JVM, Spark and batch, GPU and LLM inference, and as many integrations as possible |
| Testing | kind, KWOK and fake metrics for everything; paid write sandboxes (Karpenter, spot, GPU) small, time-boxed and approved by the Operator per phase |
| Vendor trials | Only after our part of a phase is built, to compare; read the terms first |
| Console (2026-10-21) | A React single-page app for the whole console, served by the Hub, replacing the Jinja pages once each is rebuilt. Same Tailscale identity and approver cookie, same-origin JSON API, strict CSP, model-written text rendered as text (no raw HTML, no live links), built in the image's Docker build with a pinned toolchain, nothing loaded from a CDN |
| Test lab | A persistent kind lab on the Operator's Mac: Prometheus, kube-state-metrics and load generators (diurnal, spikes, leaks, OOMs) running continuously so real history builds up, plus synthetic backfill for weeks of data |
| Usage aggregates | Kept 90 days per Contract |
| Hub MCP server | The Operator only, over Tailscale. Reads, plus Approval decisions on Proposed actions and single Sizings, the kill switch, and pull requests to the contracts repo for Automation and policy changes, which the Operator merges. Every write is audited as made through MCP. The Investigation agent never gets these tools |

## Defaults you can veto

| Choice | Default | Why |
|---|---|---|
| Persistence | Postgres 17, `langgraph-checkpoint-postgres`, psycopg 3, numbered `.sql` migrations | One database for state, checkpoints and knowledge |
| Secrets | `sops -d` at load. The Hub holds age keys for Direct Contracts only | No new library. A Relay Contract's credentials never reach the Hub |
| Many clusters | One kubernetes server per Contract, with a `cluster` argument limited to that Contract's clusters | A Contract can have dozens of clusters, and one server per cluster would multiply the tool count |
| Slack | Web API over httpx; Socket Mode over `websockets` (1.2), not slack-bolt | No public Slack endpoint, and no framework for one socket and a few calls |
| Console stack | FastAPI + Jinja + HTMX, with no JS build, until Phase 9.5; then a React app (see Decisions) | The optimizer's charts outgrew server-rendered pages |
| Console login | Tailscale identity headers from `tailscale serve`, with the console on `127.0.0.1`, plus an Operator allowlist | No passwords to manage. `serve` strips a client's copy of the header, but anything else that can reach the port (local processes, other containers on the compose network) could send it |
| Jira | An issue is created only when the Operator clicks | Never write to a client's tracker unasked |
| Budget | Monthly per Contract. Warn at 80%. At 100%, refuse new Investigations but still notify | An alert is never silently dropped |
| Model | One Hub default, overridable per Contract | |
| Similar incidents | Postgres full-text search, merged with pgvector when `AIOPS_EMBEDDING_MODEL` is set (7.4) | Unset, no embedding calls |
| Kubernetes versions | Find out each Contract's before Phase 12; the kind matrix covers 1.33+ for in-place resize | Sets what Phase 12 can rely on |
| Sizing data and Data policy | Per-Workload aggregates count as tool output under each Contract's Data policy and 6.4 masking | They leave the client network |
| Automation granularity | Per Workload, Operator only, in the contracts repo | One clear audit trail |
| In-cluster state | CRDs with our own names and schemas, rendered by the Actuator | Validation and scale over ConfigMaps |
| Clouds and distributions | Follow the Contracts' stacks; manual unit prices for on-prem | No cloud bill on RKE2 |
| Node autoscalers | Recommendations first, NodePool patches later | Patches need write access to node config |
| Cost source | List prices first; billing exports where a client grants read access | Billing needs extra permissions |

## Phases

Phases 0 to 8 were about 36 slices; Phases 9 to 19 add about 64. Phase 3 (Relay) is now a hard prerequisite of Phase 12, because every write to a client cluster goes through the Actuator, and it comes earlier if a new Contract can be reached only through a Relay. Phases 9 to 19 are outlines: each is grilled just before it is built, like every phase before it.

### Phase 0: Foundation: many Contracts, durable state (5 slices)

**0.1 Contract config.** Done.
- A pydantic schema and a loader for a contracts directory (`src/aiops_agent/contracts.py`), with `aiops contracts validate <dir>`.
- A Contract file holds:
  - its id and name;
  - its clusters: name, namespaces, and a context with an optional kubeconfig file or secret, or `in_cluster`;
  - its integrations, as a list of entries. `kubernetes` (`enable_actions`, `max_replicas`), `prometheus` (`url`, `token_secret`) and `runbooks` are builtin entries, so Phase 4 needs no migration.
- These fields mirror today's `Settings`. Unknown keys fail, so each later field arrives in the slice that gives it behaviour, and existing files stay valid:
  - tool allowlist in YAML: 4.1, when vendor tools need it. Builtins keep their list in code;
  - notification targets: 1.1 (the client channel: 1.3);
  - Data policy: 6.4 (1.3 needed none: the Operator reviews each Client report);
  - model and budget: 2.4;
  - health probe: 2.5;
  - reach: 3.2;
  - vendor source: 4.1.
- Secrets sit in `secrets.sops.yaml` and are decrypted with the `sops` binary. The checker:
  - refuses plaintext files;
  - names a bad key without ever printing its value;
  - fails when two Contracts share an age recipient. It reads recipients from sops metadata, so it needs no key.
- Two synthetic demo Contracts live in `demo/contracts/`, each with its own test-only age key. The `two_contracts` fixture loads them for every later isolation test.

**0.2 Contract-scoped tools.** Done. Its last item, a Scenario where the Contract has two clusters and the alert's `cluster` label must pick one, is `two-clusters-alert-picks-one` (2026-10-20, passes on Haiku).
- Each Contract gets its own MCP server set. The kubernetes server takes a `cluster` argument limited to the Contract's clusters, with a namespace allowlist per cluster. Runbooks come from the Contract's directory plus Shared knowledge.
- **Part 1, done: the allowlist decides read or write.** Each builtin server declares its list in code (`ACCESS`), and `open_agent` requires it. A tool not on the list is hidden, and a server's annotation can only make a tool stricter. This closed a gap: before, a server that wrongly marked a write tool as read-only skipped approval. A server that leaves the marker out was already safe, because those tools are gated.
- *Done when:*
  - the isolation tests pass: A's agent sees only A's tools, naming B's cluster errors, and Runbook search never returns B's Runbooks;
  - a tool annotated read-only but allowlisted as `write` is gated;
  - a tool annotated as a write but allowlisted as `read` is still gated;
  - a tool not on the list is invisible.
- **Part 2, done.** `build_mcp(contract, settings)` builds one Contract's tools. Isolation tests live in `tests/test_isolation.py`. The kind demo has the `bank` namespace, and a kind-backed test shows demo-bank can't read demo-shop's namespace. Until 0.3, the API, `aiops triage` and `aiops mcp` turn the `AIOPS_*` variables into one Contract named `default`.

**0.3 Contract-scoped intake.** Done.
- `POST /contracts/{id}/alertmanager` with a webhook token per Contract. Dedup is keyed by (Contract, `groupKey`). This replaces `/alertmanager` and the global token.
- The token is stored as its SHA-256 in `contract.yaml` (`aiops contracts new-token`), so the in-cluster deploy needs no sops yet: the image gains sops in 0.5. The `AIOPS_*` cluster settings are gone; `serve`, `triage` and `mcp` refuse to start if one is still set.
- Known limit: `AIOPS_MAX_CONCURRENT_TRIAGES` is shared, so one Contract's alert storm can hold every slot. Revisit with per-Contract queues when it bites.
- *Done when:*
  - A's token can't post to B;
  - the same `groupKey` in A and B starts two Triages;
  - A's group resolving doesn't make B's Proposed actions Stale.

**0.4 Postgres state.** Done.
- Tables: Investigations (with a kind column), Proposed and Executed actions, the dedup seen-set, and the audit log. Use the LangGraph Postgres checkpointer.
- Store every tool call's args and the raw result (before the cap, after redaction) so slice 2.6 can turn it into a Scenario.
- Stale deadlines are stored in the database, and timers are re-armed at startup instead of sleeping in memory.
- Rename `Triage` in code to `Investigation` with a kind. Done (part a): the API is now `/investigations`, and each record has `kind: triage`.
- *Done when:*
  - a pending approval survives a Hub restart and can still be approved;
  - a deadline that passes while the Hub is down is made Stale at startup;
  - storage tests run against Postgres in CI.

**0.5 Hub deployment.** Done.
- `deploy/hub`: docker compose with the Hub, Postgres, Caddy and a backup job. Caddy serves TLS and passes only `POST /contracts/<id>/alertmanager` (bodies up to 1 MB); everything else is a 404 there.
- The API listens on `127.0.0.1` only, with `tailscale serve` in front. Never bind it to the Tailscale interface: any tailnet device could then connect directly and forge the identity header.
- The contracts repo reaches the VM through a read-only deploy key. `update-contracts.sh` validates every Contract in the image before restarting, and rolls the clone back if one is invalid.
- The image ships pinned `sops`, checksum-verified for amd64 and arm64.
- `make hub-smoke` in CI. CI has no model key, so instead of a Report it proves: the stack is healthy, both Contracts decrypt in the image, only the alert route is public, an alert is stored and fails the way it should without a cluster, a backup restores, and a bad update is refused.
- Not covered by CI: `tailscale serve`, real certificates, the deploy-key clone, the arm64 image.

### Phase 1: Slack (4 slices)

**1.1 Slack threads.** Done.
- Each Contract has its own channel. Each Investigation is one thread that shows its status, then the Report. This replaces `slack_webhook_url`.
- Posting needs only the Web API (`chat.postMessage`, `chat.update`) with a bot token, so 1.1 uses httpx and no Slack library. Socket Mode, which receives events, moves to 1.2 with the buttons; decide there between keeping this poster and slack-bolt's client.
- *Done when:* a fake Slack client shows A's Investigations never post to B's channel.

**1.2 Approve and reject buttons.** Done.
- The buttons use the same decision path as the API (`settle`: claim, record, resume). A reject reason is entered in a modal, and the pause is claimed only on submit, so a cancelled modal decides nothing. Only the Operator's Slack user id (`AIOPS_SLACK_OPERATOR_ID`) is accepted, and only in the Investigation's own channel.
- The buttons sit on the thread's parent, not on a reply: the parent is re-rendered on every status change, so they disappear on any decision or Stale with no extra state. Each button carries its pause's deadline, so a click from an earlier pause can't decide a later one.
- Socket Mode is a small loop over `websockets` (ack each envelope, reconnect on `disconnect`); the httpx poster stays, and slack-bolt was not needed.
- *Done when:*
  - a click from anyone but the Operator is refused;
  - a second click is refused;
  - going Stale updates the message.

**1.3 Optional client delivery.** Done.
- Per Contract, `slack.client_channel` (a Slack Connect channel). A finished Report gets a **Send to client** button in the Operator's thread, and the Client report goes once, as plain text with no controls. It holds the summary, root cause, severity, affected and Recommendations. Evidence, Executed actions, the Runbook and ids never go.
- Deviations: sent on the Operator's click, not automatically, so AI output is read before a client sees it. No Data policy field: the click is the review, and masking stays in 6.4.
- A crash between claiming the send and posting it leaves it marked sent but unsent (a `ponytail:` note in `api.py`).
- *Done when:* delivery is off by default, and the client message never contains buttons.

**1.4 Questions.** Done.
- **Part a, done:** the agent answers a Question with an Answer (read tools only; write tools are hidden, not gated), a follow-up is a new message on the same thread, and the eval runner takes Question Scenarios. Two pass, with budgets set from the runs (see `docs/development.md`, Evals).
- **Part b, done:** an @mention in a Contract's operator channel starts a Question, and the Answer goes in the thread. A mention in the thread continues the same Investigation. Decided: only messages that @mention the bot (it never reads other channel traffic), Questions only read, and a Question always ends with an Answer.
- One Investigation per Slack thread (a unique index), so a redelivered mention can't start two. A follow-up claims a finished Question only with a newer mention, so two never run at once. Mentions from anyone but the Operator, in a client channel, or in a Triage thread are refused privately. A Question's thread root is the Operator's message, so the Hub only replies there.
- Widen Scenario and Expectation in the glossary and in the eval runner. A Scenario can start from a Question, and its Expectation checks the Answer's keywords and Evidence instead of a Category.
- *Done when:*
  - two Question Scenarios pass;
  - a Question in A's channel can't reach B's clusters.

### Phase 2: Web console, Tailscale only (6 slices)

**2.1 Skeleton and login.** Done.
- Login trusts the identity headers that `tailscale serve` sets. That is safe only because the console listens on `127.0.0.1` (slice 0.5).
- `/console` lists the Contracts for a login in `AIOPS_CONSOLE_OPERATORS`; anything else gets a 403, and with no operators set the console isn't mounted (404), so the in-cluster deploy stays closed. Jinja autoescapes everything, and pages send a CSP and `frame-ancestors 'none'`. `hub-smoke` proves `/console` is a 404 through Caddy even with a forged header, and renders on `127.0.0.1` from the image.
- Not covered by CI: a real `tailscale serve`.
- *Done when:* a request without the Operator's Tailscale identity is refused.

**2.2 Investigations.** Done.
- `/console` lists Investigations, filtered by Contract; each one's page shows the Report or Answer, the decisions and every tool call (args, and the redacted raw result).
- Approve and reject are plain forms (no HTMX needed), through the same decision path as the API and Slack. Each form names its pause (the deadline), like the buttons.
- **Acting needs more than the identity header.** `serve` only strips a *client's* copy of the header; anything else that reaches the Hub's port (local processes, the other containers on the compose network) could send it, and neither a network split nor tailscaled's `whois` stops that behind Docker's published port. So the header alone opens nothing but the token page (since 2.3: a forged header could read client data from tool results), and every page and every POST also needs the approver token (pasted once per browser, kept as an HMAC of it in a Secure, HttpOnly, SameSite=Strict cookie) and must be same-origin (`Sec-Fetch-Site`, or `Origin` against `Host`), which also stops CSRF.

**2.3 Ask a Question** from a form. Done.
- A form on `/console` (Contract and question) and **Follow up** on a Question's page, through the same Question path as Slack (`start_question`, `follow_up`). Same rules as acting: identity, the token cookie, same origin. The page reloads itself while the Question runs (a meta refresh, no script). A console Question has no Slack thread.

**2.4 Cost.** Done.
- **Part a, done:** every model call's tokens are recorded as it happens (a `wrap_model_call` middleware, so a resume never counts earlier Runs and a failed Run still counts), priced per call from `AIOPS_MODEL_PRICES` in USD, including Haiku's long-context tier. The console shows tokens and cost per Investigation and spend per Contract this month. Contracts gain `model:` (through the Hub's gateway) and `monthly_budget_usd:`; a budget needs its model priced at startup.
- **Part b, done:** budgets apply only where a new Run starts (alerts, Questions, follow-ups), never on a resume. At 100% the alert is still recorded (so repeats stay duplicates) and fails with the spend and budget, with no model call; Slack still hears of it. The 80% and 100% notices post once per Contract per month (`budget_notices`). Runs starting together can overshoot (a `ponytail:` note).
- *Done when:* at 100% budget, a new alert still notifies the Operator, and its Failed investigation names the budget as the reason.

**2.5 Health.** Done.
- Shows Relay connections, integration health probes, and the last successful Investigation per Contract. Also shows the effective config read-only, with secrets masked.
- `/console/health` runs one cheap read per integration through the Contract's own tools (`agent.probes`) on each load, with a 10 s limit each. Errors are redacted; check results are never shown. Config shows secret names and whether each decrypted, never values; Hub settings come out of pydantic with every `SecretStr` masked.
- Deviations: no `health probe` field in `contract.yaml` (the builtin probes are enough until a vendor integration needs its own, in 4.1), and Relay connections wait for Phase 3.

**2.6 Save as Scenario.** Done.
- Each Investigation stores its input at intake (migration 0008). The download (`/console/investigations/<id>/scenario.yaml`, identity plus token) builds the Scenario from the recorded tool calls, leaving out Runbook tools (replay reads the files). A saved Scenario names its `clusters` and `integrations`, and the replay builds exactly those with placeholder config, so it offers the tools production did; older Scenarios build byte-identical tools (fingerprinted). `--runbooks` repeats for shared plus the Contract's own.
- Turns a finished Investigation into a Scenario YAML for the Operator to download: the alert or Question, the recorded tool results, and a draft Expectation to edit. The Operator commits it to the contracts repo. The Hub never gets push access to a repo holding every Contract's secrets. The eval runner takes `--scenarios <contracts-repo>/<contract>/scenarios`.
- *Done when:* a saved Scenario replays to the same tool calls.

### Phase 3: Relay (4 slices)

**3.1 Reversed MCP connection.**
- The Relay dials the Hub over WSS and runs the MCP server over that socket. The Hub runs a `ClientSession` on its end. Both SDK sides take raw streams, so this is an adapter, not a new protocol. Each Relay token is bound to one Contract.
- *Done when:*
  - it works over in-memory streams and over a real websocket;
  - A's Relay token can't serve B.

**3.2 Relay process.**
- `aiops relay` ships in the same image, with manifests for the client cluster. Credentials come from a Secret in the client cluster. The Hub hides any tool the Relay offers that isn't on the Contract's allowlist.

**3.3 Hub side.**
- A registry of connected Relays, reconnect with backoff, and a timeout per call.
- *Done when:* killing the Relay mid-Run ends in a Failed investigation ("Relay offline") within the timeout, not a hang.
- Split 2026-11-09: **3.3a** the agent's calls through the Relay (the Hub's checks, the timeout, "Relay offline", the public route); **3.3b** the Hub's own reads through it (Sizings, node facts) and Relay state on Health and the Agenda.

**3.4 Alert forwarding.**
- The Relay accepts the in-cluster Alertmanager webhook and forwards it over the same connection.
- *Done when:* on a kind cluster with no inbound route from the Hub, a full Triage through the Relay passes the demo eval.
- 3 grilled 2026-11-08 (2 rounds, all recommended): a Relay serves one cluster (the Contract marks it `via: relay`): that cluster's kubernetes tools and its Prometheus, and the Hub's own PromQL too (hourly Sizings, node facts, Health), so the optimizer sees a Relay cluster like a Direct one; cloud and vendor integrations stay Direct. Its token is a secret the cluster names in the Contract's SOPS file (`relay_token_secret`), the same value in a Secret in the client cluster, bound to that Contract and cluster, compared in constant time and refused at startup if shared or equal to another token; rotate by changing both and restarting the Relay. It dials `wss://<domain>/relay`, a public Caddy route beside the alert route, one live connection per token (a new one replaces the old), with idle and size limits. A write needs the Hub's gate (the Contract's `enable_actions` and the Operator's approval) and the client's own switch on the Relay, off by default, its RBAC overlay matching. An alert reaching a Relay cut off from the Hub gets a 503, and Alertmanager retries; the Relay keeps no queue. Health shows each Relay cluster connected (since when, its version) or offline (since when), and the Agenda lists an offline Relay as data the Hub can't read. Live checks on the local kind lab with the Hub's direct kubeconfig removed; 3.4's demo eval on Haiku, about 0.05 USD.
- 3.1 built 2026-11-08: `relay.py`. mcp 2.3 has no websocket transport, so `bridge` turns a socket (two callables: send a text frame, receive one or None) into MCP's stream pair, one JSON-RPC message per text frame as its stdio transport frames a line; a frame that isn't one, or is over 4 MiB, reaches the session as an error and ends nothing. `serve` runs a FastMCP server over it (the Relay), `RelayTransport` a fastmcp Client (the Hub). A cluster sets `via: relay` and `relay_token_secret`, and then names none of the Hub's own credentials for it (context, kubeconfig, `in_cluster`, `allow_exec`, Prometheus URL and token): every Direct path (the Kubernetes tools, Sizing targets, probes, deploy polls, shared-store checks) skips it, and the kube client refuses it outright, since with no context the default one would be the Hub's. The Hub's `/relay` websocket names the Relay by its bearer token alone (sha256, compared with every token in constant time), refuses before the socket opens (403) without one, and keeps one live session per Contract and cluster, a new connection closing the old. At startup it refuses a Relay token under 32 characters, shared by two clusters, or equal to the approver, MCP or a webhook token. Tested in memory and over a real websocket through uvicorn on loopback; the route is not on Caddy's public port until 3.3.
- 3.2 built 2026-11-08: `aiops relay` (same image) reads `AIOPS_RELAY_*` and serves one cluster: a one-cluster Contract built from those settings, `in_cluster`, so the Hub's own Kubernetes and Prometheus servers run unchanged inside the client's network under the Hub's tool names, its namespaces enforced there as on the Hub, and the Hub's own PromQL as `hub_promql_instant` and `hub_promql_range` (never on the agent's list: the Hub's allowlist leaves them out in 3.3). Write tools are not registered unless the client sets `AIOPS_RELAY_WRITES` (the `deploy/relay-actions` overlay, with RBAC for eviction and scale only). It dials again after any drop, 1 s doubling to a minute, back to 1 s after a connection that held a minute; a refused token is logged as such, never the token. `deploy/relay` (namespace `aiops-relay`, read-only ServiceAccount bound per namespace, the token from a Secret); its image is bumped with each release.
- 3.3a built 2026-11-09: a Relay's cluster is in the Hub's own Kubernetes and Prometheus tools' cluster list (always offering Prometheus: a Relay without one answers that it has no such tool). `relay.Forward`, a middleware on the Contract's tool root inside the audit, takes a call to those tools naming a Relay's cluster, checks the namespace against the Contract (the Relay's own list may be wider), and makes the same call on that cluster's live Relay; `recent_changes` takes no namespace, so its answer is cut to the Contract's namespaces on the Hub, a GitOps object deploying anywhere else dropped whole, and the text the model reads rebuilt from what's kept; any other tool, a Sizing's included, stays local, and the Hub's local servers refuse a Relay's cluster outright. Since the Hub only lists its own tools, the Relay's `hub_promql_*` and anything else it offers never reach the agent. No Relay connected, no answer within `AIOPS_RELAY_CALL_SECONDS` (30), or the socket closing under the call is "Relay offline", and the Run fails after the call is recorded. A write needs the Relay's own switch too: with the Contract's `enable_actions` on and the Relay's off, the approved call errors. ### Phase 12: Actuator (8 slices, grilled 2026-11-09)

- 12.1 Thin slice: `aiops actuator` with its own token, pulling over HTTPS, honouring the Kill switch; an Approved Sizing resized in place on a Deployment's pods, with its ConfigMap, Kubernetes Events and the Hub's `actuations` audit trail. 12.2 The pod-creation webhook (fail open) so new pods keep the values held, and handing a container back when a person changes its template. 12.3 Pre-checks: QoS class, HPA and VPA, ResourceQuota and LimitRange, a canary pod then one at a time, `Infeasible` and `Deferred` resizes. 12.4 Auto-rollback with backoff, and Slack messages. 12.5 Automation: the Contract's `actuator:` block, `automate: true` on Sizing policy rules, the churn rule, the pause annotation, the Hub unreachable. 12.6 Revert from the console and the Hub MCP server, and the console's Automation view. 12.7 PDB-safe eviction behind the flag, in windows. 12.8 Other kinds: StatefulSet, DaemonSet, Argo Rollout in place; Job and CronJob through the webhook only.
- Grilled 2026-11-09 (all recommended, three rounds):
  - **Shape.** The Actuator is its own Deployment in each client cluster whose Contract names an `actuator_token_secret` for it, with its own ServiceAccount and token (bound to the Contract and the cluster), so the Relay keeps its read-only identity; it works for Direct clusters too. It refuses to start below Kubernetes 1.33. Every minute it pulls its desired state (`GET /actuator/desired`: the Approved Sizings, later the Automation Sizings, and the Kill switch) and reports outcomes (`POST /actuator/reports`), plain HTTPS through the Hub's public boundary; the Hub never pushes. This amends ADR 0004's "over the Relay connection".
  - **No CRDs.** The Hub is the only source of truth: a client's GitOps can't read the private contracts repo, and Approved Sizings never pass through git, so CRDs would be a second copy kept in sync by our own code. The Actuator keeps what it applied in one ConfigMap in its own namespace, writes Kubernetes Events on the Workloads, and the Hub keeps the audit trail. Its RBAC: `patch pods/resize`, `create pods/eviction` (12.7), its own ConfigMap, `create events`, its own webhook's `caBundle`; never `patch deployments`, which could change images.
  - **What it changes.** Requests only (limits stay `keep`), never above the limit, never a change of QoS class (skipped, with an event). In place first; the fail-open webhook gives new pods the values held; eviction only behind the Contract's flag (off), inside a window, only where an in-place resize is `Infeasible`, one pod at a time, at least 5 minutes apart, through the Eviction API so PDBs hold, never to make room.
  - **How long values last.** An applied Approved Sizing stays held after it stops being current, until a later approval, Automation or a Revert (resized back to the template's values in place). "Current" now means waiting to be applied: one superseded before it was applied never is. A person changing the template's requests wins: the container is handed back (`HandedBack`). While the Hub is unreachable, the Actuator keeps what it holds and changes nothing new (an event after 15 minutes). The Kill switch stops resizes and evictions, and the webhook lets pods through unchanged; nothing is reverted at once. Locally: scale the Actuator to zero (the webhook fails open) or annotate a Workload `aiops-actuator/pause: "true"`.
  - **Safety.** An HPA on a resource's utilization: that request is left alone. A VPA in any mode but `Off`: the Workload is skipped. Over ResourceQuota or outside LimitRange: skipped, never clamped. A canary pod for 10 minutes, then one at a time; `Infeasible` stops that Workload, `Deferred` waits 10 minutes. Rollback within an hour of a resize on an OOM kill, a restart, or 2 minutes NotReady: resized back in place, then no new Sizing of that container for 24 hours, doubling; 3 rollbacks in 7 days end Automation of the Workload. "Adoption threshold" is dropped: the canary covers it.
  - **Automation.** `automate: true` on a Sizing policy rule, under the Contract's `actuator:` block (`eviction`, `timezone`, `windows` of days and hours, which gate eviction only). Changes under 10% are ignored; increases apply at once, decreases at most once a day per container.
  - **Seen.** The Hub's `actuations` (90 days), the console's Automation view with Revert, `revert_sizing` on the Hub MCP server; Slack only for a rollback or an end of Automation, resizes in the daily digest.
  - CRDs and their rendering from the contracts repo are dropped; KWOK goes to Deferred. The live check on kind comes after 12.4.

### Phase 14: Horizontal (5 slices, grilled 2026-11-12)

- 14.1 HPA and KEDA minimum replicas from percentiles. 14.2 Weekly profiles with lead time. 14.3 Re-anchoring the HPA target after a Sizing changes requests. 14.4 Backtests with an error budget.
- Grilled 2026-11-12 (three rounds, all recommended):
  - **Read-only.** The Hub recommends and the client's GitOps applies: nothing in this phase writes to an HPA or a ScaledObject, and no permission is added (Argo CD with self-heal and Flux both put a patched HPA back unless told to ignore the field). Only Workloads that have an HPA or a KEDA ScaledObject; one with a fixed replica count gets nothing yet. Everything is read from Prometheus (kube-state-metrics' HPA series), as Sizings are; KEDA through the HPA it creates (`keda-hpa-<name>`), since KEDA has no metric for a ScaledObject's minimum, maximum or target. Writing a minimum is Deferred, with its own grill and an ADR (a new Actuator write).
  - **Need.** The HPA's own "desired replicas" never reads below its minimum, so the Hub computes what a Workload needed: current replicas x current value / target value, for any metric the HPA scales on (resource, per container, pods, object, external), the largest when it has several. "Unknown" where the series are missing, for a Workload with two HPAs, or a per-container metric on a kube-state-metrics older than v2.19.0 (no `container` label). The Hub stores each Workload's peak need per hour itself (one table, kept 8 weeks, filled at first from what Prometheus still has), because a weekly profile needs more weeks than most Prometheus keep.
  - **Floor (14.1).** A low percentile of the hourly need over the Workload's Sizing policy's window: the 10th under `production`, the 25th under `high-availability`, a policy setting; none under `off`. Never below 2 unless today's minimum already is; a minimum of 0 (KEDA's scale to zero) is left alone. Shown against today's minimum: a saving when lower, a risk when higher. Its saving is its own line, the replica-hours removed priced at the Sizing's requests, so it adds to Waste without counting a replica twice; available only, and realized once kube-state-metrics shows the HPA's minimum lowered. One risk line when the need was above the HPA's maximum ("needed more than its maximum in 6% of hours"); no maximum is recommended.
  - **Requests under an HPA (14.3).** A Sizing of a request an HPA divides by (`Utilization`, cpu or memory) is marked "held by its HPA" (today the Hub shows it as available and the Actuator skips it), with the one-time change that frees it: the target as `AverageValue`, the same threshold as an absolute number (the target percentage times the pod's summed requests, all containers; one container's for a per-container metric). After it requests play no part in the HPA and the Actuator resizes freely: it only ever skipped `Utilization` targets. For KEDA's HPA, the same change on the ScaledObject's trigger (`metricType: AverageValue`); a wrong guess of whose HPA it is only shows the wrong snippet. Its Waste still counts: one manifest line recovers it. Phase 13's rule stays: no OOM step-up for a container whose memory an HPA scales on. The Actuator never patches a target percentage.
  - **Weekly profile (14.2).** For each hour of the week, the median of that hour's need across the stored weeks (one odd week changes nothing), never below the Floor; shown as blocks of hours with one Floor each, in `sizing.timezone` (new, UTC by default), each block starting `sizing.lead_time` early (new, 15 minutes by default; measuring it per Workload from its pods' time to Ready can come later). For a KEDA Workload, a ready `cron` trigger per block to paste into its ScaledObject (KEDA takes the trigger asking for most replicas); a plain HPA has no schedule of its own and gets the profile with a note saying so. No generated CronJobs that patch `minReplicas`.
  - **Backtest (14.4).** The newest full week replayed hour by hour against a profile built from the three before it, so a profile needs 4 stored weeks. Error: the replica-hours it was off by, too few plus too many, as a share of the replica-hours needed; both parts shown, and the cost of the too many. Budget: 20%, fixed (a setting once real backtests show what is normal). Over it the Workload shows "load isn't weekly enough" and keeps only its Floor. A gap under 10% is nothing the HPA acts on (its tolerance, both ways).
  - **Seen.** The console's Sizing views (the Floor beside each autoscaled Workload, its profile, backtest and the manifest change to copy) and one line in the weekly digest. The Triage agent's sizing tool is unchanged: no eval rerun.
  - **Terms.** *Floor*: the minimum replicas the Hub computes for a Workload with an autoscaler. *Weekly profile*: its Floors by hour of the week. A Sizing stays per replica.
  - **Slices.** 14.1a: HPAs read from kube-state-metrics, each Workload's hourly need stored; a load generator with a weekly pattern started in the lab, for 14.4's live check four weeks on. 14.3: Sizings held by an HPA, with the `AverageValue` change (early: it frees savings on autoscaled Workloads at once); live check on kind (an HPA switched, the request cut, the replica count unchanged). 14.1b: the Floor, its saving and risks, the console and the digest line. 14.2: the Weekly profile, `sizing.timezone`, `sizing.lead_time`, KEDA's `cron` triggers. 14.4: the backtest and its budget, tested on a synthetic Monday peak. Cluster Autoscaler and Karpenter both, named per cluster in the Contract (`cluster-autoscaler`, `karpenter` or none: their rules differ, and guessing from which metrics exist is a guess); a cluster with neither still gets the report ("a person could remove this node"). Computed by the Hub each hour and stored, as Sizings are; a new Nodes page in the console and one line in the weekly digest. The Triage agent's tools are unchanged: no eval rerun. No new permission in a client's cluster and no spend.
  - **Blockers (15.1).** Read from Prometheus (each pod's node, each node's room and taints, PodDisruptionBudgets' allowed disruptions, pods with no owner) plus what the Actuator already reads in its namespaces (pods and PodDisruptionBudgets): it sends the Hub, hourly, only the pods that have a Blocker, capped in size and checked as its reports are (12.9c). kube-state-metrics has no series for emptyDir or hostPath volumes or for which pods a PodDisruptionBudget covers, and pod annotations only when allowlisted, so a cluster without an Actuator gets what Prometheus has and "unknown" for the rest. Cluster Autoscaler's Blockers are its documented list (a PodDisruptionBudget allowing no disruption, kube-system pods without one, a pod with no controller, local storage, `safe-to-evict: "false"`, a pod that fits nowhere else); Karpenter's are its `karpenter.sh/do-not-disrupt` annotation and PodDisruptionBudgets only (its docs don't say a pod with no controller blocks it). Computed twice: with today's requests, and with the requests after the Sizings, which says which nodes go if the Sizings are applied (a Sizing frees capacity, but money is saved only when a node leaves). Its own figure with its monthly cost, never summed with Savings: after the Sizings it is partly the same money.
  - **Proposals (15.6).** Per Blocker, the change that removes it, ready to copy (a PodDisruptionBudget for a Workload with none, the annotation that lets a local volume be dropped, and so on), and the autoscaler's setting to check, named but not compared: the Hub can't read it (kube-system, or objects of no namespace). The Operator turns one into a pull request with the Hub MCP server's existing tool. The descheduler isn't proposed: its `HighNodeUtilization` must be paired with a scheduler scoring `MostAllocated`, and the default scores `LeastAllocated`.
  - **DaemonSet Sizing per node (15.3).** One Sizing per group of nodes of the same instance type (the label the Hub already reads for list prices) instead of one pooled over every node, which fits the busiest and is too large on the rest. The Actuator can't read a node, so the Hub sends each group's node names with its Sizing and the Actuator applies each pod's by its node, in place; a new pod carries its target node from its creation (the DaemonSet controller's node affinity), so the webhook gives it its group's requests when lower than its template's, as today's rule has it. A pod on a node the Hub hasn't seen yet keeps the template's requests until the next run names its node. One approval covers all of a DaemonSet's groups; a group with too little history is still learning.
  - **The node-capacity cap** (parked here since 9.1): a Sizing's request is never above the largest node's room after its DaemonSets, with the risk "needs a larger node".
  - **Placement (15.2).** The webhook adds a preference, never a requirement (a required rule can leave a pod Pending), for nodes with a label the client names in the Contract (`actuator: placement`, absent: off), such as a small node pool kept for pods that can't move; the report treats those nodes as where Blockers belong and never proposes removing them. For every Workload the report names as blocking, in the Actuator's namespaces, which the Hub lists for it as it does Sizings; the pause annotation and the Kill switch stop it. ### Phase 16: Spot (6 slices, grilled 2026-11-12)

- 16.1 A spot ratio per Workload with an on-demand floor. 16.2 Placing replicas by capacity type. 16.3 Fallback on interruption.
- Grilled 2026-11-12 (four rounds; all recommended but CronJobs on spot, which the Operator chose to build in this phase rather than defer). "Floor" is Phase 14's term, so 16.1's on-demand floor is the *On-demand minimum* here.
  - **Scope.** Recommend first, then act: the Hub prices spot and shows candidates, then the Actuator's webhook places each new replica; nothing in a manifest changes (a topology spread balances two groups evenly, so a manifest can't hold a 70/30 split; Karpenter's documented recipe for it says itself that it "is not identical" to a ratio). The Operator sets it in the Contract, on the Sizing rule that picks the Workload: `spot: {ratio: 0.7, on_demand: 2}`; the Hub only shows where to look. Its own setting, not tied to Automation; it needs an Actuator and the cluster's spot label. Deployments and Argo Rollouts with 2 or more replicas, and CronJobs by their own rule; never a StatefulSet (its state and volumes) or a DaemonSet; a rule naming a kind that can't is refused.
  - **The numbers.** On-demand replicas: the larger of the On-demand minimum and the share that isn't spot, rounded up ("70% on spot, but never fewer than 2 on-demand": 10 replicas give 3 and 7, 4 give 2 and 2). The minimum is 1 or more, so no Workload is ever all on spot.
  - **Placing a replica (16.2).** The On-demand minimum is a requirement, "not on a spot node" (the one requirement the webhook adds; Placement's are preferences); the spot share is a preference, so a spot replica that finds no spot room lands on on-demand by itself and fallback needs no code, as Karpenter launches on-demand when a NodePool allowing both has no spot. On Cluster Autoscaler a preference isn't counted when it picks a node group to grow, so whether new nodes are spot is the client's expander setting: said in the guide. Spot is a node label the Contract names per cluster (`karpenter.sh/capacity-type=spot`, `eks.amazonaws.com/capacityType=SPOT`, `cloud.google.com/gke-spot=true`, `kubernetes.azure.com/scalesetpriority=spot`); on-demand is any node without it (`NotIn` matches a node that lacks the label); on AKS, whose spot nodes are tainted, the webhook also adds the toleration to spot replicas. Counted per ReplicaSet, so each new version reaches the ratio by itself (counted over the Workload, old pods would leave the new version short of on-demand ones), on-demand replicas first, the count corrected against the cluster each minute (the docs don't say a Deployment's pods are admitted one at a time).
  - **Keeping it.** Scale-down: on-demand replicas get a higher `controller.kubernetes.io/pod-deletion-cost` at creation, so spot ones go first and the minimum survives (best effort, Kubernetes says; the mix leans to on-demand until pods are created again); a Workload that sets deletion costs itself is left alone. Drift (a spot replica that fell back, pods created while the Actuator was down) is repaired by nobody until the next rollout or scale-up: the Hub shows intended against actual and a risk line below the minimum ("restart to repair"); the Actuator never evicts for it. The webhook stays fail-open, so while the Actuator is down the ratio and the minimum are best effort. The Kill switch and the pause annotation stop new placements; running pods stay. A Workload Phase 15's report names as blocking gets no spot replicas, and the Hub says why.
  - **Interruptions (16.3 as first written).** After one, the ReplicaSet creates new pods and the webhook places them again: nothing to build but 12.10 (Phase 12), without which a spot interruption in a Sizing's watch hour is a false Rollback. Notice is 2 minutes on AWS, 30 seconds on Azure, 0, 30 or 120 seconds on GCP.
  - **CronJobs on spot.** Only through a rule that names `kind: CronJob`, written `spot:` with no ratio and no minimum (one with either is refused): a batch run that starts again from zero is a judgement of its own. Only a CronJob whose Job allows a retry (`backoffLimit` of 1 or more; the default is 6), others skipped with the reason shown. Every pod of a run prefers spot on its first try; once the run has a failed pod its retries are required off spot, so a run is interrupted once at most. A Job of no CronJob stays skipped. Decided 2026-11-12, to build with 16.3: a run's pod that Failed because it was evicted to drain its node (`EvictionByEvictionAPI`, how Karpenter empties a spot node it is about to lose) is no Rollback either; 12.10 left it counting.
  - **Money.** Spot nodes are priced as on-demand today, so a cluster with spot shows too high a cost: first a discount typed per cluster in the Contract (one field, every cloud), later spot list prices (Azure's Retail Prices API, public; GCP's catalog with the API key it already needs; AWS's `DescribeSpotPriceHistory` with the Contract's own credentials, never its undocumented public feed). kube-state-metrics must allowlist the spot label, as it does the instance type. The Bill check counts spot nodes at their discount and includes the bill's spot lines, for all three clouds, or a cluster that moves to spot stops reconciling. Candidates, from what the Hub already reads: a Deployment or Rollout with 2 or more replicas on average, no persistent volume, not named as blocking; and CronJobs. Each shows a what-if (70% spot with a minimum of 2; a CronJob run entirely on spot) in its own figure, an upper bound, never summed with Savings: nothing is saved unless a spot pool exists and the autoscaler shifts nodes to it.
